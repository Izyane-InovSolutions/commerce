# Known gaps

> What the backend does not do yet, and defects found while writing these docs, ranked by impact. Each item links to the module doc that has the code references.

**How these were found.** By reading the code on 2026-09-29, not by running it. Items marked ✔ were checked again by hand against the source. The others come from careful reading, but a failing test should confirm each one before it is fixed. Items that the [2026-09-25 audit](../github-issues-backend-audit-2026-09-25.md) raised and that are **still true** are included here.

**Resolved since that audit.** Password-reset emails are now sent, through the email pipeline ([background-processing.md](background-processing.md#email-delivery-pipeline)).

## High impact

These can lose money, lose or corrupt stock, or leave customers stuck.

| #      | Gap                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Where                                                                                |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| H1 ✔  | **A late mobile-money approval can leave a paid order unpaid.** The stock hold and the gateway approval window are both 15 minutes. When the reservation expires, the order stays `PENDING_PAYMENT`. A success applied afterwards then fails in `confirmPayment`, because `commit` rejects an `EXPIRED` reservation: the customer is charged and the order never becomes PAID. Nothing cancels abandoned pending orders either                                                                                                                                    | [orders](modules/orders.md#known-gaps), [flows](flows.md#key-rules-along-the-way)    |
| H2 ✔  | **Payments settle only when someone asks.** Webhooks are rejected, because `verifyWebhook` is not implemented, and `PaymentsService.reconcile` has no route and no sweeper. A pending payment that no client polls through `POST payments/:id/status` stays pending indefinitely                                                                                                                                                                                                                                                                                  | [payments](modules/payments.md#known-gaps), [integrations](integrations.md#payments) |
| H3 ✔  | **No refund can complete.** `UnifiedPaymentProvider.refund` returns 501 and `Pending` returns 503, so every refund case ends in `FAILED`. Returns, cancellations and admin refunds all stop there                                                                                                                                                                                                                                                                                                                                                                 | [payments](modules/payments.md#known-gaps)                                           |
| H4     | **Refund cases can get stuck in `PROCESSING`.** Once a case reaches `PROCESSING` (after reconciliation, or after a crash just before the provider call), `retry`, `processPending` and `reconcile` all ignore it                                                                                                                                                                                                                                                                                                                                                  | [payments](modules/payments.md#known-gaps)                                           |
| H5     | **A cancelled gateway payment stays pending here.** Every gateway status other than `SUCCESS` or `FAILED` maps to `PENDING`, so a gateway-side `CANCELLED` or `EXPIRED` payment is never reflected                                                                                                                                                                                                                                                                                                                                                                | [payments](modules/payments.md#known-gaps)                                           |
| H6 ✔  | **Goods-receipt reversal can be applied twice.** A reversal receipt is itself `POSTED`, and nothing marks it as un-reversible. Reversing it removes the stock and the PO's received quantity a second time                                                                                                                                                                                                                                                                                                                                                        | [procurement](modules/procurement.md#known-gaps)                                     |
| H7 ✔  | **Admin stock adjustment can push available stock below zero.** It only checks `on_hand >= 0`, not `on_hand >= reserved`. It also stores `abs(delta)`, so the movement log loses the direction. It has no `Idempotency-Key`, and it records no actor                                                                                                                                                                                                                                                                                                              | [inventory](modules/inventory.md#known-gaps)                                         |
| H8 ✔  | **Admin fulfillment cancellation on seller-mode orders.** It is not limited to platform orders, and passes a null warehouse into `returnCancelledStock`                                                                                                                                                                                                                                                                                                                                                                                                           | [fulfillment](modules/fulfillment.md#known-gaps)                                     |
| H9     | **Fulfillment quantity checks can be bypassed.** Admin cancel ignores quantity already booked onto a shipment. Platform pack ignores cancelled quantity. Both end in a database CHECK failure (`cancelled + dispatched <= allocated`) at dispatch                                                                                                                                                                                                                                                                                                                 | [fulfillment](modules/fulfillment.md#known-gaps)                                     |
| H10    | **Manual tracking events skip the workflow.** Staff can post `CANCELLED`, `DISPATCHED` or `BOOKED` as ordinary events. That changes the shipment status without releasing or dispatching fulfillment quantity                                                                                                                                                                                                                                                                                                                                                     | [shipments](modules/shipments.md#known-gaps)                                         |
| H11    | **Seller refund reversals can make the available balance negative.** The reversal always debits `balance`, even when the sale is still held                                                                                                                                                                                                                                                                                                                                                                                                                       | [financials](modules/financials.md#known-gaps)                                       |
| H12    | **Returns that silently never refund.** Accepted items with no seller order are skipped, so the return sits in `REFUND_PENDING` with no refund case. Seller-mode items are also restocked into the platform warehouse                                                                                                                                                                                                                                                                                                                                             | [returns](modules/returns.md#known-gaps)                                             |
| H13    | **Checkout idempotency is weak.** The key is optional. A replay with a different body returns the old order instead of 409. After a definite failure, a retry with the same key replays that failure                                                                                                                                                                                                                                                                                                                                                              | [checkout](modules/checkout.md#known-gaps)                                           |
| H14    | **Fulfillment provisioning can drop lines.** Every P2002 is treated as a harmless replay, and items it cannot resolve are skipped without a log, so a paid line can end up with no fulfillment                                                                                                                                                                                                                                                                                                                                                                    | [fulfillment](modules/fulfillment.md#known-gaps)                                     |
| H15 ✔ | **Deleting an offer deletes order history.** `OrderItem.offer` is `onDelete: Cascade` ([schema.prisma:964](../../services/commerce-api/prisma/schema.prisma#L964)), and so is variant → offer. An admin who deletes a product, variant or offer therefore deletes the matching order lines, unless a `Restrict` key such as a fulfillment line, PO line or review blocks it. When one does block it, the error is not mapped and the admin gets a 500                                                                                                             | [products](modules/products.md#known-gaps), [offers](modules/offers.md#known-gaps)   |
| H16 ✔ | **`reserve` can block on its own caller's lock.** `sweepExpired` and `expireReservation` run on their own connection, outside the caller's `tx` ([inventory.service.ts:487-489](../../services/commerce-api/src/modules/inventory/inventory.service.ts#L487-L489), [:755](../../services/commerce-api/src/modules/inventory/inventory.service.ts#L755)). Take an order with two lines on the same variant, where an expired reservation still exists: the second sweep waits on the row lock the order transaction already holds, until the transaction times out | [inventory](modules/inventory.md#known-gaps)                                         |

| #     | Gap                                                                                                                                                                                                                                                     | Where                                                                            |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| R1 ✔ | **The outbox has no publisher.** Events are written but never delivered                                                                                                                                                                                 | [background-processing](background-processing.md#outbox)                         |
| R2    | **Failed carrier webhooks are never retried.** A delivery marked FAILED keeps its dedupe row, so a retry is acknowledged but not processed. A P2002 is caught inside an aborted Postgres transaction                                                    | [shipments](modules/shipments.md#known-gaps)                                     |

| R5    | **Reservation sweeping inside a caller's transaction.** `sweepExpired` and `expireReservation` open their own transactions even when `reserve` runs inside the caller's `tx`                                                                            | [inventory](modules/inventory.md#known-gaps)                                     |

## Data integrity and API consistency

- **Destructive deletes.** Admin deletes of products, variants, offers, attribute values and warehouses cascade into order, cart, wishlist or stock rows. See [products](modules/products.md#known-gaps), [offers](modules/offers.md#known-gaps), [catalog](modules/catalog.md#known-gaps) and [inventory](modules/inventory.md#known-gaps).
- **Seller offers can draw platform stock.** A seller can create an offer with `stockSource: PLATFORM` and sell from the platform's shared stock. See [offers](modules/offers.md#known-gaps).
- **Submission status can be bypassed.** Staff can publish a PENDING or REJECTED seller product through `updateStatus`. See [products](modules/products.md#known-gaps).
- **Error codes.** Every status outside the mapped set (422, 501, 502 and so on) returns the error code `INTERNAL_ERROR`. See [architecture](architecture.md#request-lifecycle).
- **Pagination.** It is inconsistent: `OfferPage` uses its own shape, and many lists are unpaginated (`GET /orders`, `GET /returns`, admin products, payout accounts, wishlist). See the module docs.
- **Operations metrics.** They mix currencies and apply the warehouse filter unevenly, and refunds from every source are counted. See [operations](modules/operations.md#known-gaps).
- **Admin order status filter.** `GET /admin/orders?status=` is probably rejected by `forbidNonWhitelisted`. See [orders](modules/orders.md#known-gaps).
- **Reviews moderation.** Editing clears a FLAGGED state, and a user can never report the same content again after a dismissal. See [reviews](modules/reviews.md#known-gaps).

## Configuration drift

- `SELLER_PAYOUT_PROVIDER` is validated but never read. `SCHEDULED_WORKERS_ENABLED` and `UNIFIED_PAYMENTS_ALLOW_HTTP` are read but not validated.
- `.env.example` is missing several variables. See [configuration.md](configuration.md#drift).
- `PAYMENT_FX_BASE_CURRENCY` can be set, but the converter assumes ZMW.
- `CacheService` exists, but no module uses it.

## Not built yet

These features have no backend implementation (from the audit, still true):

- Payment webhooks and refunds against the live gateway, and automated payouts. Payouts and carriers are manual-only adapters.
- Customer order cancellation and reorder.
- Choice of shipping option at checkout: one quote per group.
- Promotions and coupons; loyalty and gift cards.
- Push notifications and device tokens.
- Support cases.
- Search facets, autocomplete and a search index.
- Buy Box ranking.
- Make-an-offer and auctions; dynamic pricing.
- Seller SLAs and scorecards; fraud and risk scoring; recommendations.
- Admin audit-log reader; low-stock alerts (`reorderPoint` is stored but nothing uses it).
- Mobile-money identity lookup at payout-account setup. The gateway supports it; see [integrations.md](integrations.md#payments).
- An API for procurement documents (the model exists).
- A CI workflow (`.github/workflows` does not exist).
